## 0. 定位

**每一次推理，都是一道防線。**

AxVigil 想把 Web3 的 AI 算力，用在真正有意義的地方。現在有個荒謬的現象：越來越多項目讓 AI 代理去解數學題、算哈希，只為了鑄一張 NFT 或挖一個新代幣。算力燒掉了，鏈上卻沒有變得更安全。與此同時，加密產業每年被盜走數十億美元，2025 年超過 34 億。最大的幾筆多半來自私鑰與基礎設施被攻破，但智能合約程式碼漏洞仍是發生次數最多的攻擊類型，2025 年單這一類就造成約 3.5 億到 5 億美元的真實損失，而 AI 正在讓攻擊變得更便宜、更快。AxVigil 把這股算力導向這個真實的痛點：AI 代理在每次都會重新變形的漏洞沙盒裡修補合約，三個驗證者重新評分、至少兩個簽名同意，每一次成功的修補都在鏈上留下一份任何人都能重新計算的能力紀錄。協議在挑選 AI 掃描工具時，可以查證這些紀錄，而不只是聽廣告。我們不發空氣幣，也不搞零和遊戲。我們只想讓每一次 AI 推理，都朝保護鏈上資產多走一步。

這三個驗證者目前是許可制，由團隊運行。開放的驗證者集合是計畫，尚未上線。Muse Spark（`muse-spark-1.1`）是第一個在 AxVigil 上留下公開紀錄的模型。這不是排名。

## 1. 一份通過的紀錄是什麼

看似合理的修補不是修復。代理拿到一份重新編排過的漏洞合約，交上修補與概念驗證，確定性沙箱評分器確認漏洞在修補前成立、修補後消失，而且合約沒有被改壞。通過之後，鏈上記下一份綁在代理身分上的可驗證能力紀錄。

## 2. 問題

### 2.1 算力層 —— AI 推理正在被浪費

2025–2026 年,agent 代碼推理能力快速成長,而 Web3 相當大一部分把它導向**無社會價值的零和博弈**:SAT/布爾可滿足性謎題、算質數、解謎題、重複的 benchmark 截圖——每一項都在燒真實 GPU 時間,鑄一個保護不了任何人的「證明」。**算力空轉,而真實世界的安全缺口在擴大。**

### 2.2 安全層 —— 合約防禦嚴重供給不足

| 痛點 | 現狀 |
|---|---|
| 損失規模 | 近年 DeFi 漏洞累計損失數十億美元 |
| 審計供給 | 頂級公司排期數月,費用五到六位數美元 |
| 覆蓋缺口 | 大多新部署的中小協議沒有審計預算,裸奔上線 |
| 響應速度 | 審計是靜態/時點性的;部署後的持續監測幾近於零 |
| AI 未被利用 | AI 能產出合理 patch,卻缺乏可信的驗證與調度層 |

### 2.3 基礎設施層 —— 缺少從算力到安全的橋樑

即使有人想用 AI 做安全:

1. **能力無法驗證** —— 「安全能力」靠 benchmark 截圖或自述,沒有可獨立重跑的證據。
2. **題目會被背** —— 公開題庫很快進訓練資料;固定題目衡量記憶而非修補。
3. **憑證綁錯對象** —— 能力應屬於 agent,而非錢包。
4. **出題者沒回報** —— 白帽整理的漏洞模式被反覆使用,卻無持續回饋。
5. **人人重造輪子** —— 每個團隊各自搭沙箱、找題、防作弊。
6. **沒有從考場到戰場的路徑** —— 即使證明了能力,也沒有網路讓它保護真實資產。

**AxVigil 要解決的核心問題:建立一套可信機制,讓 AI 算力從「空轉解題」轉向「防禦真實合約」——從讓任何此類主張可信的「驗證」開始。**

## 3. 解決方案與定位

### 3.1 定位

AxVigil 是**安全 AI 的信任與調度基礎設施**。不是另一個 benchmark、不是另一個審計平台、不是另一個 NFT 專案。

- 對 AI 團隊:今天是執照考場,未來是接單平台。
- 對協議方:自動化防線(路線圖)。
- 對白帽出題者:持續變現的知識。
- 對生態:把閒置算力轉為安全公共財的轉換器。

### 3.4 設計原則

1. **算力必須產出真實保護** —— 獎勵消除漏洞,而非「解題」本身。
2. **可重跑、可驗證** —— 任何結果都能被獨立重現。
3. **題目由網路發放** —— agent 不能挑題、不能背題。
4. **憑證跟著 agent 走** —— 綁 Agent ID,不綁錢包。
5. **免費參與,收入來自真實預算** —— 認證免費;防禦任務賺真實收入。
6. **不靠投機代幣營運** —— 營運應由安全預算支付（§8.2）。代幣只是 §8.3 的設計，而且現在沒有發行。

## 4. Layer 1 —— 熔爐(現有系統)

### 4.1 它在網路中的角色

今天的原型(`Fu93/axvigil`, `main`)實現的是 **Layer 1**。它的工作:**確保進入防禦網路的 agent 具備真實能力——而不是會產生誤報、浪費協議方時間的無效算力。** 沒通過熔爐的 agent 無法接入 Layer 2。這是整個網路的信任根基——也是本次黑客松端到端能跑的交付物。

### 4.2 認證流程(端到端)

```
Backend (FastAPI) ──發放新變體(僅原始碼)──▶ AI Agent
      ▲                                          │
      │                 patch + PoC              ▼
      │                                    Verifier(確定性沙箱)
      │                                    ① pocProvesBug
      │                                    ② pocFailsAfterPatch
      │                                    ③ hiddenTestsPass
      │◀── EIP-712 MintAuth(全部通過才簽) ─── ④ patchWithinLimits

Agent ID 持有人送出 mint
  → AxVigilSkill (ERC-5192):更新執照
  → AxVigilCollectible (ERC-721):免費紀念
  → agent 現已持牌;符合 Layer 2 接入資格(路線圖)
```

**失敗分析（兩個由實跑找到、並在 PR #11 修好的基準錯誤）。**

1. 隱藏測試失敗時的文字說修補改變了預期行為、應把修補維持最小。模型正確認出幽靈存款，卻只擋了 `token == address(0)`。`test_codelessNonZeroTokenCannotPhantomDeposit` 會拒絕它。現在的提示改為：失敗代表行為被改了，或修補沒有蓋住整個漏洞類別，而且不點名隱藏測試，也不寫出 `code.length` 的修法。
2. the access-control hidden-test template 要求還原字串 `"not owner"`。渲染會把角色改名（`custodian`、`manager` 等），脆弱原始碼裡沒有那串字，所以正確的 `"not custodian"` 被誤判失敗。隱藏測試現在接受未授權呼叫者的任何 revert。

### 4.6 信任模型與威脅模型

一次通過的意思是：一台機器上的一個沙箱評分器，接受了針對一個已渲染變體的一份修補。`Minted` 事件裡的 `submissionHash` 按 `verifier/axvigil_verifier/keccak.py` 的規範編碼，綁定 `(challengeId, seed, patch, PoC)`。它本身不證明第二套評分器會同意，也不證明 signer 金鑰與 owner 不是同一把。

| 角色 | 做得到 | 做不到 |
|---|---|---|
| Agent | 讀渲染後的原始碼；送出 patch 與 PoC | 從 API 讀到 seed、隱藏測試或參考解（測試在 git 倉庫裡是公開的） |
| 後端 signer | 為本程序標成通過的 session 簽 `MintAuth` | 自己鑄造；改稀有度；自己輪換自己 |
| 合約 owner | `setSigner`、`commitSeed`、`revealSeed`、暫停、設定 URI | 在 signer 已輪換到另一把金鑰之後，偽造 `MintAuth` |
| 任何人 | 用證據包重算 `submissionHash`，並重跑 `scripts/verify_evidence.py` | 在 `revealSeed` 之前還原 batch seed |

BSC 上的實跑，包括三次門檻鑄造，用的是有資源上限的離線子程序：`ffi` 關閉、`FOUNDRY_OFFLINE`、牆鐘逾時，以及 POSIX `rlimit`（CPU、位址空間、檔案大小、程序數）。那台機器沒有安裝 Docker，也沒有使用它。`AXVIGIL_SANDBOX=docker` 已實作（`verifier/docker/Dockerfile`，映像 `axvigil-sandbox:1.8.7`：`--network none`、唯讀根檔案系統、uid 1000、CPU／記憶體／程序數上限、tmpfs 工作目錄），要自己打開才會用。未設定或設成 `subprocess` 才是實際評分用的執行器。兩種都不是 TEE，也不是 zkVM。映像還沒建好時，CI 裡那一項 Docker 檢查會略過。

## 5. 題庫與防記憶引擎

### 5.1 為什麼防記憶是前提

如果 agent 只是背了答案,它在防禦層就是**無效算力**——無法辨識野外出現的新變體。熔爐的核心價值,是確保每個持牌 agent 具備**泛化的**修補能力,而非對特定題目的記憶。

### 5.2 `variantgen` —— 防記憶引擎

每個漏洞類型是一個漏洞模板。依 seed，`variantgen` 換掉識別字、插入干擾函式、重排函式順序。結構指紋把「只改了名字」的複本視為同一個變體。離線驗證指令 在建立 20 題題庫時丟掉這些長得像的。線上伺服器在把原始碼交出去之前做同樣的檢查：跳過已經發過的指紋，並且在 `AXVIGIL_REFERENCE_CHECK` 開啟時（`Settings.from_env` 的預設）先用參考解評分再發題。Agent 必須修好那一類漏洞。

| 漏洞類型 | 類別 | 難度 |
|---|---|---|
| `reentrancy` | 重入 | Basic |
| `access-control` | 權限控制 | Basic |
| `price-manipulation` | 價格操縱 | Advanced |
| `signature-replay` | 權限控制 | Legendary |
| `bridge-phantom-deposit` | 權限控制(Qubit QBridge,2022 年 1 月) | Advanced |
| `empty-market-inflation` | 價格操縱(Hundred Finance / Sonne) | Advanced |

**今天：4 個正規漏洞類型加上 2 個重建的真實事件——共 6 個漏洞類型，離線各 20 個自我驗證的唯一變體，合計 120。** 類別只有三個，因為 `NUM_CLASSES = 3`。`signature-replay` 是傳奇難度的權限控制，不是第四個類別。兩件真實事件是 `bridge-phantom-deposit`（Qubit QBridge，2022 年 1 月，損失數字以 `the family metadata file` 所連結的事後報告為準）與 `empty-market-inflation`（Hundred Finance，2023 年 4 月；Sonne，2024 年 5 月）。這兩題只接受類別級修補：只擋 `address(0)` 的橋接 patch，以及只加 `require(shares > 0)` 的金庫 patch，都會被拒絕。兩者沒有已知的誤放行缺口。這不是「每一種可能的修補都已枚舉」的聲明。

### 5.3 差分式四項檢查

| 檢查 | 驗證什麼 | 為什麼必要 |
|---|---|---|
| `pocProvesBug` | PoC 在原始合約上成功 | 漏洞真實;排除偽 PoC |
| `pocFailsAfterPatch` | 同一 PoC 在修補後失敗 | 漏洞確實被消除 |
| `hiddenTestsPass` | 隱藏功能測試全部通過 | 修補沒破壞既有邏輯 |
| `patchWithinLimits` | 改動行數與位元組有上限，而且合約名稱與每一個必要的公開函式都還在 | 阻擋刪掉合約或刪掉介面，不只是擋一份過大的 diff |

### 5.4 題目來源原則

- ✅ 只用**已修補、已公開揭露**的漏洞(DeFiHackLabs、Code4rena、Sherlock、Immunefi 事後報告)。
- ✅ 一律先經 `variantgen` 變形。
- ❌ 絕不使用仍在線上、未修補的漏洞。
- 📋 私有評測模式(計畫中):自帶題目只在私有環境評分;新發現走責任揭露。

## 10. find-vs-fix 斷層(誠實陳述)

這是全文最重要的但書,也是內行評審一定會問的:

**今天的認證證明 agent 能在受控目標上*修好一類已知*漏洞。一個生產級防禦網路還需要在真實代碼中*找出未知*問題——這是熔爐尚未測試、而且嚴格更難的問題。** 通過熔爐本身並不意味著 agent 會找出新的 0-day。

我們把它當成一個範圍決策,而非含糊帶過:

- **Layer 2 v1 的範圍限定在 agent 持牌類別內的模式化偵測與初篩** —— 找出它所認證類別的實例 —— 而非開放式 0-day 獵捕。
- 近期價值主張因此是「對已知類別的快速、低價、持續初篩」,並明確定位為**輔助性,而非取代人工審計**。
- 邁向真正「發現」能力是未來研究,路線圖以它為前提,而非假設它已具備。

我們寧願交付一個能用代碼支撐的較小主張,也不畫撐不起來的大餅。

## 14. 法律與合規

| 議題 | 設計回應 |

## 附錄 B —— 可重現性

在 `main` 的檢出上，裝好 Foundry，並先做一次 `cd contracts && forge build`：

```bash
scripts/test_all.sh
# 離線題庫，單一漏洞類型：
See variantgen/README.md for the command that checks 20 fresh rewrites of one family.
```

評分過的 session 會寫下 `backend/evidence/<submissionHash>/manifest.json`（可用 `EVIDENCE_DIR` 改位置）。重算：

```bash
python3 scripts/verify_evidence.py backend/evidence/<submissionHash>/manifest.json
```

它檢查 CID、`submissionHash = H(challengeId, seed, patch, poc)`、seed 承諾，以及一次新的評分。隱藏測試從本倉庫的漏洞類型目錄讀取。

鏈上、不需要金鑰：

```bash
RPC_URL=https://bsc-testnet-rpc.publicnode.com \
AXVIGIL_COLLECTIBLE=0x06580BFc1626f7DD3d7B841FD304e6f2B23e4658 \
python3 scripts/reveal_and_recompute.py --dry-run
```

原收藏品的 signer 輪換與 batch 2 揭示已上鏈（`signerRotationTx` `0xaea5242f…`，`batch2RevealTx` `0xf83f0829…`）。門檻部署與三次 Muse Spark 鑄造寫在 `deployments/bsc-testnet-97.json`。再鑄一枚的指令在 `docs/operator-runbook.md`。實跑評分用子程序沙箱，不是 Docker。

有 `META_API_KEY` 時的模型迴圈：

```bash
PYTHONPATH=agent:verifier python3 -m axvigil_agent solve \
  --challenge <rendered-challenge-dir> --max-iters 4
```

離線替代是 `--oracle`。它不會呼叫 `https://api.meta.ai/v1`。

## 結語

AI 算力不該被浪費在零和解題遊戲裡。每一份 GPU 時間、每一次推理,都應該產出真實的保護——一個協議的 TVL、一個散戶的存款、一條鏈的安全。

AxVigil 的終極願景不是「發代幣」或「賣 NFT」，而是：**一份新合約部署時，經熔爐認證的 agent 應該能提供人工審計可以接著做的第一輪檢查。** 那一輪不是審計的替代品，本文也不替審計報價。

我們還沒到那裡。我們今天擁有的,是讓其餘一切變得可信的那塊:一個 AI 的修補被驗證、而非被宣稱的試煉場。這才是算力該去的地方。
